## 一、一句话定位

**让客服在买家开口之前，先看见这个人。**

右侧辅助区不再是一个空白插件位，而是一块"**进线前 3 秒就能读完的买家全景卡**" + 一块"**主管视角的风险雷达**"。

### 主线设计：不是做更好的客服机器人，是做更好的客服外挂

赛题原文明确说"**摒弃传统机械问答机器人**"，痛点是客服"**看不清、跟不上、判不准**"。所以我们的系统**不替客服回话，只让客服看得清、说得准**。

| 赛题三件套 | 我们的对应模块 |
|---|---|
| 懂用户 | 会话理解 Agent（意图 / 情绪 / 诉求 / 证据） |
| 助人工客服 | 右侧接待辅助插件 |
| 控风险 | 风险预警跟踪看板 |

## 二、数据事实 → 设计决策（这一节是方案的根）

我把官方数据全量解析了一遍。**下面每一条都是从真实数据里算出来的，不是猜的**——这份"用数字说话"的能力本身就是评审第 2 项（大模型智能分析准确度）的得分点。

### 2.1 数据资产总览

| 表 | 行数 | 关键字段 | 说明 |
|---|---|---|---|
| 聊天记录 | **998 条 / 138 会话** | 会话ID、消息序号、发送时间、角色、买家昵称、scene_major、scene_minor、message_text、内容类型、image_path、关联订单号、关联工单号 | 每会话 4–10 条，平均 **7.2 条**；买家 487 / 客服 495 / 系统推送 16 |
| 订单 | 113 行 × 19 列 | 订单号、会话ID、商品、金额、订单状态、快递、物流单号、赠品、买家留言 | 一行一单 |
| 补发换货工单 | 24 | 售后原因、原/补发物流单号、客诉加急、工单状态 | 漏发赠品 7 / 错发色号 5 / 直播承诺赠品 3 |
| 线下打款工单 | 13 | 打款类型、退款问题类型、金额、支付宝账号、转账状态 | **待审核 7 笔 / 转账成功 6 笔** |
| 物流工单 | 15 | 问题类型、处理方案、发货仓、工单状态 | 破损/拦截改址/签收未收到/短少/停滞各 3 |
| 不良反应工单 | 10 | 年龄、肤质、使用商品、**产品批次号**、不适部位、症状、是否就医 | **3 条已就医**，风险等级最高 |
| 售后退货工单 | 18 | 包裹类型、退货原因、签退建议、**是否异常** | 异常 9 / 正常 9 |

**关联关系（官方数据说明原文）**：聊天 ↔ 订单 ↔ 工单 三向可通过 `会话ID` / `订单号` / `工单号` 关联；**一个会话至多一笔订单、至多一张工单**。→ `[确定]` 关联模型简单，不需要图数据库。

### 2.2 八个事实，八个设计决策

| # | 从数据里读出来的事实 | 对应设计决策 |
|---|---|---|
| 1 | **官方已给 `scene_major`(10类) / `scene_minor`(41类) 标注**，998 条全覆盖、零缺失 | ① 直接作为意图识别的 label taxonomy；② **更重要的是——白送一套评估基准**，可以真算准确率 |
| 2 | **客服消息 495 条，去重后仅 323 条，重复率 35%**；Top1 话术"好的亲，还有其他可以帮您的吗"用了 14 次 | 把"话术同质化率"做成**可量化的管理指标**，这是"千人一面"痛点的硬证据 |
| 3 | 买家消息中**只有 18% 带订单号、37% 带工单号** | 客服必然反复问订单信息 → "**一屏看全**"信息聚合卡是刚需 |
| 4 | **88 / 138 个会话**至少命中 1 类风险信号，**38 个会话命中 ≥2 类** | 风险看板不是锦上添花，是 64% 的会话都需要 |
| 5 | 风险信号分布：时效催促 **46 会话**（最高频）> 过敏/不良反应 12 > 投诉举报 9 > 正品质疑 4 > 赔偿诉求 3 | 风险要**分级**：安全类（不良反应）> 舆情类（投诉/正品）> 体验类（催促） |
| 6 | 不良反应 10 条中：**B5面膜 3 例、修护精华 2 例、焕活礼盒 2 例**；**批次号"00"出现 3 次** | 做"**商品/批次维度的不良反应聚类**"——真实业务里最有价值的功能，技术上只要 group by |
| 7 | 图片 29 张，已按 10 类命名：`broken_pump / short_item / broken_parcel / wrong_shade / refund_screenshot / live_promise / missing_item / swatch / logistics_screenshot / consult_card` | 做"**证据一致性校验**"：买家说"泵头坏了"却发色卡图 → 提示客服索要正确证据。这是全场最容易被记住的创新点 |
| 8 | 工单未闭环 **28 张**（补发 4 + 打款 7 + 物流 5 + 不良反应 4 + 退货 8）；其中**打款工单 7 笔待审核** | 做"**闭环跟踪看板 + 超时升级**"，直接对应赛题的"状态跟踪"要求 |

### 2.3 官方已经给了评测答案

这是最容易被忽略、但价值最大的一点：

- `scene_major` / `scene_minor` = **意图识别的 ground truth**
- `image_path` 的目录名 = **图片分类的 ground truth**
- `售后退货工单.是否异常` = **风控标签**
- `不良反应工单.是否就医 / 症状描述` = **安全风险等级标签**

⚠️ **但必须守一条纪律**：这些标注**只能用于评估，不能喂给模型当输入**。否则就是自欺欺人，评委一问就穿。我们的做法是——Agent 自己判断，再和标注对比，把对比结果写进 PPT。**能拿出"我们错了 12 个，错在哪、为什么"的队伍，比自称"准确率 95%"的队伍可信一百倍。**

## 四、系统架构与 Agent 链路

### 4.1 四层架构

```
① 数据层    聊天记录 998 / 订单 113 / 5 类工单 80
                ↓
② 关联层    纯代码，零 Token
             按 会话ID / 订单号 / 工单号 三向 join
             按 买家昵称 拉历史会话（识别重复进线）
             产出：SessionContext（结构化对象）
                ↓
③ 智能层    S1 理解 Agent → S2 风险 Agent → S3 决策 Agent
                ↓
④ 应用层    右侧接待辅助插件（客服）/ 风险预警跟踪看板（主管）
```

**关键工程判断：第 ② 层绝对不要用 LLM。** 关联、聚合、去重、时间排序——这些是 SQL 三行解决的事，交给大模型既慢又贵还会错。这一条本身就是"成本优化"项的具体得分点。

### 4.2 三个 Agent 的职责

| Agent | 输入 | 输出 | 用什么模型 | 成本档 |
|---|---|---|---|---|
| **S1 理解** | SessionContext（本会话全部消息 + 关联订单 / 工单） | 意图（major/minor + 置信度）、实体（订单号 / 物流号 / 商品 / 金额 / 时间）、情绪等级 1–5 + 依据原文片段、买家真实诉求、图片类型 + 与描述一致性 | 文本小模型 | 低 |
| **S2 风险** | S1 输出 + 规则引擎结果 | 四类风险分（0–100）+ 触发依据 + 建议动作 | 文本强模型 | 中 |
| **S3 决策** | S1 + S2 输出 + RAG 检索结果 | 处置方案（含依据条款）+ 三档语气候选回复 | 文本强模型 | 最高（但只在需要时调） |

**规则引擎与人机协同**：硬风险词（"就医""投诉""315""曝光""差评"）直接由规则置为高危，不等模型；模型负责"软风险"判断。`[确定]` 这是防止幻觉的最后一道闸。

### 4.3 必做的工程护栏

| 风险 | 护栏 |
|---|---|
| LLM 编造订单号 | **后置硬校验**：抽取出的订单号 / 物流单号必须能在数据库里命中，否则丢弃并标记 `[未能匹配]` |
| LLM 输出格式崩坏 | Pydantic v2 + JSON Schema 强约束 + 失败重试 1 次 + 再失败降级到规则输出 |
| Demo 现场 API 断网 | 预热缓存全部 138 个会话的推理结果；提供"离线回放模式"开关，断网也能演 |
| 响应太慢 | 关联层同步返回快照，智能层异步补齐（先给客服看订单卡，1–2 秒后补风险分） |

## 五、模块一：智能接待辅助插件（右侧辅助区）

参考工作台实拍图：右侧"接待方案"栏下方那块灰色"插件"区域，就是本次的设计目标位。

### 能力 1｜买家 360 全景卡（消灭"信息孤岛"）

一屏之内，自上而下四块：

| 区块 | 内容 | 数据来源 |
|---|---|---|
| 身份条 | 买家昵称 · 历史进线次数 · 累计实付 · 敏感标签（敏感肌 / 孕妇 / 曾过敏） | 订单 + 不良反应工单聚合 |
| 订单条 | 当前订单：商品 / 金额 / 状态 / 物流 / 收货地 / 赠品 / 买家留言 | 订单表 |
| 工单条 | 该会话关联工单的类型 / 原因 / 状态 / 处理人 / **已等待时长** | 5 类工单表 |
| 历史条 | 上次进线时间 + 上次结论一句话（**重复进线时自动高亮**） | 同买家历史会话 |

> 设计依据：事实 #3——只有 18% 的买家消息带订单号。客服现在必须手工去三套系统里捞，这块卡把它变成 0 次操作。

### 能力 2｜意图与情绪实时解读

- 输出 `scene_major` / `scene_minor` + 置信度（对标官方 10/41 类体系）
- 情绪等级 1–5，**必须附原文依据片段**（可点击跳转到那句话）
- 买家真实诉求：退款 / 补发 / 要解释 / 要安抚 / 只是问问

### 能力 3｜三档共情回复建议（解决"千人一面"）

不生成一条回复，生成**三条不同温度**的候选，让客服挑：

| 档位 | 适用情绪 | 风格 |
|---|---|---|
| 安抚档 | 情绪 ≥4 级 | 先认情绪再解决，高道歉密度、短句 |
| 专业档 | 情绪 ≤2 级、咨询类 | 结构化给信息，含成分 / 使用 / 适配说明 |
| 效率档 | 常规物流、退款进度 | 直接给结论 + 下一步 + 时效承诺 |

**硬约束**：生成的回复必须过一遍"**与官方知识库一致**"的校验（售后政策、补发时效、退运费承担规则），防止模型乱承诺。

### 能力 4｜证据一致性校验（多模态亮点）

1. 买家发图 → 用视觉模型识别图片类型（对标 10 类目录：泵头破损 / 错发色号 / 色卡 / 退款截图 / 直播承诺截图 / 物流截图 …）
2. 与买家文字描述做一致性比对
3. 不一致时**主动提示客服**："买家描述为泵头破损，但图片疑似色卡，建议索要破损部位特写"

> 这一条是全场最容易被评委记住的功能——**它把"客服反复要图"这个真实痛点做成了 AI 可执行的动作**，而且我们有官方图片类型目录做支撑。

## 六、模块二：风险预警跟踪看板

### 面板 1｜实时风险雷达（会话级）

- 四类风险分 + 综合等级（红 / 橙 / 黄 / 绿）
- 高危会话自动置顶，显示触发依据原文
- 点击跳转到对应会话

| 风险类型 | 判定信号（来自真实数据） | 数据支撑 |
|---|---|---|
| **安全风险**（最高） | 不良反应关键词 + 就医提及 + 商品/批次命中历史不良反应 | 12 会话命中，10 张不良反应工单，3 条已就医 |
| **舆情风险** | 投诉 / 曝光 / 举报 / 差评威胁 / 正品质疑 | 9 会话投诉 + 1 差评 + 4 正品质疑 |
| **资金风险** | 重复退款 / 待审核打款久挂 / 仅退款可疑 / 拆封少件 | 打款 7 笔待审核 + 退货异常 9 条 |
| **体验风险** | 时效催促 / 重复进线 / 长时间未响应 | 46 会话催促 = 最高频风险 |

### 面板 2｜商品安全聚类（业务洞察，我们的差异化）

- 按 **商品 × 批次号** 聚合不良反应工单
- 输出："测试 B5 多效修护面膜 20 片"累计 3 例反馈，其中全脸泛红 3 例
- **批次号异常检测**：3 条工单批次号为 `00`（缺失/异常），自动标记为**数据质量问题**并提示补录

> 这个面板的价值不在技术难度，在于**它做了真人运营会做的事**——评委里的业务专家一眼就能看懂，而且会认。

### 面板 3｜工单闭环跟踪

- 28 张未闭环工单按"已等待时长"排序
- 超时阈值分级告警（`[待确认]` 具体阈值需按店铺 SLA 定，建议补发 24h / 物流 48h / 打款 4h）
- 显示卡在谁手上（处理人 A01–A05、B07/B12、G001–G003）→ 可做坐席工作量视图

### 面板 4｜管理洞察仪表盘（给客服主管）

| 指标 | 我们算出来的基线 | 目标 |
|---|---|---|
| 话术同质化率 | **35%**（495 条客服消息仅 323 条不同） | 用三档回复后下降 |
| 风险会话占比 | 64%（88/138） | 高危 100% 被拦截 |
| 待闭环工单 | 28 张 | 超时率归零 |
| 平均信息查阅次数 | 当前需跨 3 套系统手工查 | 降至 0 次 |

## 七、技术栈

### 7.1 选型总表

| 层 | 选型 | 理由 | 状态 |
|---|---|---|---|
| **大模型（文本）** | 阿里云百炼平台上的 Qwen 系列（强 / 小双档） | 赛题明确鼓励阿里开源模型；国内直连无网络风险 | `[待确认]` 具体型号与计费，需在百炼控制台查当前可用清单 |

| **结构化输出** | Pydantic v2 + JSON Schema | 保证 LLM 输出可解析、可校验 | `[确定]` |
| **后端** | FastAPI + Uvicorn | 轻、快、自带 OpenAPI 文档，演示友好 | `[确定]` |
| **实时推送** | SSE（Server-Sent Events） | 单向推风险事件，比 WebSocket 简单一半 | `[确定]` |
| **数据存储** | SQLite（单文件） | 免部署、源码交付简单；决赛拷过去就能跑 | `[确定]` |
| **检索** | 关键词 + 规则优先，**不上向量库** | 998 条数据 + 41 类意图，向量检索是负收益 | `[确定]` |
| **前端** | React + TypeScript + Vite + Ant Design + ECharts | 表格 / 看板 / 图表开箱即用，省 3 人天 | `[确定]` |
| **部署** | Docker Compose + 一键启动脚本 | 决赛要交源码 + 运行指南 | `[确定]` |

### 7.2 一条重要提醒：千牛插件**不要**真去接

`[推测]`（但方向明确）真正的千牛插件需要走阿里开放平台 ISV 入驻 + 应用审核，周期以周计，**参赛期间大概率来不及，且会拖垮进度**。

**我们的做法**：做一个 **1:1 复刻千牛工作台的高保真页面**，右侧留出可插拔的插件容器。理由：
1. 赛题只说"官方提供客服工作台示意图及说明"——**是参考，不是要求接入**
2. 演示效果完全一致（评委看的是能力，不是审批单号）
3. 风险为零

> 如果队友坚持要接真插件，让他先去确认审核周期 `[待确认]`，别在方案会上争。

### 7.3 不要做的事（省下来的都是命）

| 不做 | 为什么 |
|---|---|
| 不微调模型 | 998 条数据微调必过拟合，得不偿失 |
| 不建向量库 | 数据量小到关键词匹配就够 |
| 不做用户登录 / 权限 | 比赛 Demo 不需要，赛题也没要求 |
| 不做移动端 | 客服工作台是桌面端 |
| 不接真实支付 / 真实物流 API | 数据全是 MOCK，接了也没用 |

## 八、量化评估体系（这是拉开差距的核心）

绝大多数队伍会在 PPT 里写"我们的系统效果良好"。**我们要写数字，并且写清楚数字是怎么来的。**

### 8.1 六项指标

| # | 指标 | 怎么算 | 数据来源 | 需不需要人工标注 |
|---|---|---|---|---|
| 1 | 意图识别准确率 / macro-F1 | 预测 `scene_minor` vs 官方标注（138 会话） | **官方已给** | 不需要 |
| 2 | 情绪等级识别 F1 | 3 人交叉标注 138 会话情绪等级 → 算 Cohen's κ 一致性 → 对比模型 | 需自建 | 3 小时 |
| 3 | 风险召回率 / 误报率 | 3 人标注"应否预警" → Recall（召回优先）/ Precision | 需自建 | 2 小时 |
| 4 | 话术同质化率 | 生成回复的重复率 vs 基线 **35%** | **官方已给** | 不需要 |
| 5 | 关键实体漏检率 | 订单号 / 物流单号抽取的漏检率（可自动比对） | **官方已给** | 不需要 |
| 6 | 单会话 Token 成本 | 实测，按分级路由 / 无路由两组对比 | 实测 | 不需要 |

### 8.2 评估的三个"专业动作"

1. **主动说明样本量限制**：138 个会话，95% 置信区间约 ±8%。**主动写出这句话，比藏起来强一百倍**——它证明你懂统计，而不是只会调 API。
2. **给混淆矩阵 + 错误案例**：挑 5 个错得最典型的会话，分析"为什么错"（是标注边界模糊？还是模型没抓住口语化表达？）。
3. **做消融对比**：有 RAG / 无 RAG，分级路由 / 全量强模型——用数字证明每个模块都有用，而不是堆功能。

## 九、成本优化机制（评审加分项）

| 机制 | 做法 | 省在哪 |
|---|---|---|
| **分级路由** | 简单意图（会员积分、好评回访、物流查询）走小模型；安全 / 舆情风险才升级强模型 | 约 70% 会话不需要强模型 |
| **关联层零 Token** | join / 聚合 / 去重全用 SQL，不进 LLM | 最大的成本节省点 |
| **上下文只给必要字段** | 不把 19 列订单全塞进 prompt，只给 6 个相关字段 | 输入 Token 直降 |
| **增量摘要** | 新消息到达只更新增量，不重跑全量会话 | 长会话省最多 |
| **结果缓存** | 按 `(会话ID, 最后消息序号)` 缓存，重复访问零成本 | 演示时几乎免费 |
| **结构化输出** | JSON Schema 约束输出长度，禁止模型写小作文 | 输出 Token 可控 |
| **图片按需调用** | 只在消息含 `image_path` 时调 VL（仅 29 条） | 视觉调用量降 97% |
