# 千牛插件形态与数据通路说明

> **回答两个会被评委直击的问题**：① 你们做的是千牛右侧插件吗？② 一个网页怎么实时拿到千牛的数据？
> **日期**：2026-09-27 ｜ **触发**：团队 review 时提出质疑
> **用途**：PPT 素材 + 答辩问答准备 + 内部口径统一

---

## 〇、结论先行（三句话）

1. **形态上我们是对的，但要指对入口** —— 上游 agent-desk 自带 `/workbench` 路由，它就是"坐席工作台"形态（细图标栏 + 会话列表 + 聊天/详情分栏），**天然对应千牛三栏**；我们的四个抽屉就长在它的右侧详情位。⚠️ 但演示时若误开 `/dashboard/conversations`（带左侧功能大菜单），会立刻变成"网站后台"的第一印象。
2. **独立网页确实拿不到千牛的实时数据——但比赛不需要拿**。官方交付物是 PPT + Demo + 视频，**不是千牛插件包**；比赛数据也是官方提供的 MOCK，没有真实店铺和账号可接。
3. **★ 真接千牛插件，学生团队在"资格"层面就过不了** —— 不是"来不及"，是"不可行"。这条论据比"审核周期长"硬得多，**必须写进 PPT**。

## 一、官方到底要求什么（原文与图示）

### 1.1 赛题原文（已核实）

> **右侧辅助区（插件与生态能力 - 📌本次比赛设计目标区域）**
> 定位：这是客服的"百宝箱"。它的核心目的是**在不干扰核心聊天流程的前提下**，为客服提供**即时的决策辅助和快速操作工具**。

配套示意图（`交接包-欧莱雅黑客松/06-工作台参考截图.png`）：右侧是一整块灰色区域，中间写着"**插件**"二字，旁边还有"智能表单"等标签页 → **说明该区域本身是千牛的多标签插件容器**。

### 1.2 关键解读：赛题要的是"设计能力"，不是"上架插件"

| 赛题实际要求 | 赛题**没有**要求 |
|:---|:---|
| 在右侧辅助区这个**位置**，设计出辅助客服的**能力**（讲清定位、交互、价值） | ❌ 注册 ISV、提交千牛插件上架审核 |
| 交付**PPT + 演示视频 + 现场可运行 Demo** | ❌ 交付千牛插件安装包 |
| 评分维度要求"**基于现有工作台规划**" | ❌ 在真实千牛客户端里跑起来 |

**结论**：做高保真复刻是**合规的**，前提是——**把"复刻"讲成主动选择，而不是能力不足的妥协**。这个讲法怎么组织，见第五节。

## 二、我们现在的实际形态（实测，非文档转述）

### 2.1 两个入口，形态完全不同

| 路由 | 布局 | 视觉印象 | 该不该用来演示 |
|:---|:---|:---|:---|
| `/dashboard/conversations` | 带 `AppSidebar`（左侧功能大菜单：客户管理/知识库/AI 配置…） | **网站后台** | ❌ **不要** |
| **`/workbench`** | `WorkbenchRail`（左侧细图标栏，仅"会话/工单"两项）+ `WorkbenchHeader`（顶栏），**无功能大菜单** | **坐席工作台** | ✅ **用这个** |

### 2.2 一个容易被忽略的事实（对它有利）

`web/app/workbench/page.tsx` **只有 5 行**，且 `git status` 显示该目录**一行未改**：

```tsx
import { ConversationWorkbench } from "@/app/dashboard/conversations/_components/conversation-workbench";

export default function WorkbenchPage() {
  return <ConversationWorkbench />;
}
```

**这意味着**：`/workbench` 是**上游 agent-desk 原生自带的坐席工作台路由**，上游自己就区分了"管理后台"和"坐席工作台"两种形态。我们改造的三栏组件被两边复用——**这不是我们拼凑的，是上游的既有设计** `[确定]`。

### 2.3 三栏结构对照

`ConversationWorkbench` 内部使用 `ResizablePanelGroup`（可拖拽分栏）实现：

| 千牛三区 | 我们的对应物 | 状态 |
|:---|:---|:---|
| 左侧列表区（客户接待管理） | `WorkbenchRail` + 会话列表面板 | ✅ 已有 |
| 中部核心区（沟通与交互） | 聊天窗口 + 顶部会话信息条 | ✅ 已有 |
| **右侧辅助区（插件与生态能力）** | **我们的四个抽屉**（会话洞察 / 客户全景 / 回复建议 / 会话信息） | ✅ **本次比赛目标区，已实现** |

**结论**：三栏结构是**齐的**。缺的不是结构，是**"让评委一眼看出对应关系"**——这靠一页对照图解决，不靠改代码。

## 三、为什么不做真插件：★ 资格门槛（硬论据）

原方案给的理由是"**ISV 入驻 + 审核周期以周计，来不及**"。这个理由**偏软**——听起来像"我们懒"或"时间不够"。

查阿里开放平台官方准入规则后，发现了**更硬的理由**：

| # | 准入门槛（官方规则） | 学生团队能满足吗 |
|:--|:---|:---|
| 1 | 开发者账号绑定的支付宝须为**企业实名认证** | ❌ 需企业主体 |
| 2 | 已上架服务**评分 > 4.5 分** | ❌ 需先有已上架服务 |
| 3 | 服务期内**付费用户数**：客服/数据类目 **> 500**，其他类目 > 1000 | ❌ **这一条直接封死** |
| 4 | 申请商家**必须入驻聚石塔** | ❌ 需企业级云资源 |
| 5 | 插件上架审核**每次 10 个工作日** | ⚠️ 即使前 4 条过了，时间也紧 |

**结论**：这是一条**资格门槛**，不是**时间门槛**。一支学生队伍在准入规则第 1、3 条上就无法满足。

> **PPT 里的表述建议**：
> "千牛插件的接入是一套企业级准入体系（企业实名、服务评分、付费用户规模、聚石塔入驻）。我们的目标不是绕过它，而是**先把右侧辅助区该有什么能力做出来、并且证明能力可迁移**——因为业务逻辑层与数据来源是解耦的（见第四节）。"

## 四、数据通路：网页怎么"看到"千牛的数据

这是最尖锐的一问，分两层回答。

### 4.1 第一层：技术真相——独立网页**拿不到**

真千牛插件运行在**千牛客户端内的插件容器**里，数据由**宿主（千牛）通过 JS-API 喂给插件**，并受淘宝授权体系约束。**一个跑在浏览器里的独立网页，没有这条通道，也拿不到授权。**

所以"我们的网页实时读取千牛"这个说法**本身就是错的**——不能说，也不能写进 PPT。

### 4.2 第二层：但比赛**不需要**拿，而且我们的架构已经为"将来能拿"留好了口

**比赛为什么不需要**：
- 官方数据是虚构 MOCK 数据（店铺"测试美妆旗舰店"），**没有真实店铺、没有真实千牛账号可接**
- 交付物是 Demo + PPT + 视频

**我们的架构为什么是对的**：

```
【现在（Demo）】                      【将来（生产）】
官方 MOCK xlsx                        千牛开放平台 API
      ↓                                      ↓
 pipeline.py（离线段）                数据同步适配器（在线段）
      ↓                                      ↓
   ┌───────────── 以下是同一套业务逻辑，一行都不用改 ─────────────┐
   │  ② 关联层   三向 join → SessionContext                     │
   │  ③ 智能层   S1 意图 / S2 风险 / S3 建议                     │
   │  ④ 应用层   右侧四抽屉 + 风险看板                            │
   └──────────────────────────────────────────────────────────┘
```

**关键论证**：我们的②③④层**不关心数据从哪来**——它们只消费"结构化的会话上下文"。所以从 MOCK 切到真实千牛，**替换点只在最上层的"取数适配器"**。

这正是"数据源与业务逻辑解耦"的价值，也是 PPT 里可以正面回答"真实场景适配性"质疑的答案。

### 4.3 真实接入路径（如果要继续做下去）

| 步骤 | 做什么 | 前置条件 |
|:--|:---|:---|
| 1 | 入驻淘宝/千牛开放平台（`open.taobao.com`） | **企业实名支付宝** |
| 2 | 创建千牛插件应用，获取 `AppKey` / `AppSecret` | 上一步通过 |
| 3 | 在插件中心申请**千牛开发环境**，绑定测试账号 | 上一步通过 |
| 4 | 按官方 JS-API 列表 / 交互规范开发（H5 / Hybrid QAP） | — |
| 5 | 提交审核上架（10 个工作日） | 满足全部准入规则 |

**关于"实时性"的技术说明** `[待确认]`：
- 千牛是数据驱动平台，订单/消息变化会**推送到客户端**，客户端据此更新数字角标、跳转插件（来源：阿里千牛团队公开技术分享）
- 另有一处官方文档提到"客户端与服务端数据交互目前以**客户端主动拉取**为主"（上下文为"实时数据库"模块）
- 这两处口径不完全一致，**不写进 PPT**，除非拿到一手文档核实。答辩若被问到，回答："具体实时机制以千牛开放平台的 JS-API 与消息协议为准，我们已按'事件驱动刷新'设计前端，订阅方式可替换。"

## 五、演示口径：三件事必须做

### 5.1 演示入口统一为 `/workbench`

**这是最低成本、最高收益的一处修正。**

- ✅ `http://localhost:8083/workbench` → 细图标栏 + 会话列表 + 聊天 + 右侧四抽屉 = **工作台**
- ❌ `http://localhost:8083/dashboard/conversations` → 多一个左侧功能大菜单 = **后台**

同一套代码，两个路由，**第一印象天差地别**。

> 建议：演示脚本（`运行手册.md`）里把入口 URL 固定为 `/workbench`，并加一句核对："确认页面左侧**没有**功能大菜单"。

### 5.2 PPT 加一页「三栏对照图」

左边放官方示意图（`06-工作台参考截图.png`），右边放我们的 `/workbench` 截图，**用箭头标出三条对应关系**，右侧区高亮。

**这一页解决的是**：评委不用自己在脑子里做映射。第一眼就看出"右侧区就是设计目标区，他们做出来了"。

### 5.3 PPT 加一页「数据通路与接入路径」

内容就是第四节那张"现在 vs 将来"的图 + 资格门槛表。

**这一页解决的是**：把"你们怎么接真实数据"这个必问题，从被动应答变成主动展示——**并且展示出团队知道门槛在哪、路径怎么走**，这比"我们接了真数据"更显专业。

## 六、一句话总结

> **形态是对的，但要打开`/workbench`而不是`/dashboard`；真插件在资格上做不到（不是时间问题）；网页拿不到千牛数据是正常的，因为比赛用的是 MOCK，而我们把"取数"和"业务逻辑"做了解耦——将来换成真数据，业务代码一行不用改。**
>
> **说白了：我们没有假装接上了千牛，我们展示的是"如果接上了，能力长什么样"。这个讲法是站得住的。**
